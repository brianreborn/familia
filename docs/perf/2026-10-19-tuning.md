# Performance tuning pass, 2026-10-19 (miryam + the agent box)

**Every number here is low-precision: 1 rep per point** (coarse binary-search sweep, as in the other perf docs).
Differences under ~10 % are noise; the box numbers are noisier still (shared VM, other agents' jobs).
Raw logs and the driver live in familia-private `logs/2026-10-19-perf/`.

## Setup

| | miryam | box (agent VM) |
|---|---|---|
| CPU | i5-7200U, 2C/4T, 15 W (`cpu MHz` never read above 2500, i.e. base clock, during the run) | 8 vCPU Xeon (Sapphire Rapids class, AVX-512/AMX), KVM |
| RAM | 7.1 GiB + zram, earlyoom | 15.6 GiB (3-9 GiB free, shared with other agents) |
| llama.cpp | b11374 native build (CPU); b11374 Vulkan prebuilt for the iGPU points | b11374 ubuntu-x64 prebuilt (CPU) |
| Models | Laya Q8_0 (decision, encoder), LFM2.5-1.2B Q4_K_M (general), Qwen3.5-2B Q4_K_M (coder) | same three + Qwen2.5-0.5B Q4_K_M, Qwen3.5-0.8B Q4_K_M (new, 508 MiB, draft candidate) |
| Guard rails | `nice 19`, `ionice -c3`, one model at a time, `systemd-run --user --scope MemoryMax=3500M MemorySwapMax=256M` | same priority; no user cgroups, so an RSS watchdog (2600 MiB, then 3500 MiB) |

Driver: an unattended queue (`perf_soak.py`, private repo) that, per model, sweeps threads, then ubatch
(using the best threads), then flash-attn x KV type at depth, then load mode (mmap / none / mlock), then a
depth curve and sustained long runs (pp1024 + tg256 on miryam, tg512 on the box) with temperature, `cpu MHz`
and throttle-counter sampling every 3 s. Sweeps are coarse binary search: both ends, the middle, keep the
better half, halve again.

## Findings

1. **miryam: 2 threads, not 4, for every model.** Hyper-threads hurt generation (LFM2.5 tg 12.95 at 2 vs
   9.29 at 4; Qwen3.5-2B 6.5 vs 5.2) and do not help prefill. 3 ties 2 on the 2B. This matches the
   graph's coder `threads: 2`; no change needed.
2. **ubatch barely matters on miryam** (all values 64-512 within 10 % for pp1024); 256 is a safe default.
   On the box 256-512 beat 64 by 15-30 %, and 1024 was slower for the Qwen3.5 models.
3. **q8_0 KV costs prefill everywhere on this build**: at depth 2048 on miryam LFM2.5 pp 20.1 vs 36.3
   (f16, FA on), Qwen3.5-2B 22.5 vs 25.8; on the box Qwen3.5-2B pp@d4096 110 vs 373 and tg 16.7 vs 26.9.
   Generation on miryam is unaffected (within noise). The coder keeps q8_0 because the 65536 context needs
   it on a 7 GiB host (graph `override_reasons`); for short-context nodes f16 is faster.
4. **Flash-attn off was as good or better for CPU generation at moderate depth** (miryam LFM2.5 tg@d2048
   11.8 off vs 8.2 on; Qwen3.5-2B 6.5 vs 6.0). Prefill is equal. q8_0 V needs FA on (llama.cpp refuses
   otherwise), so the coder's `flash_attn: true` stays.
5. **mmap roughly adds the file size to RSS for repacked quants.** With the default mmap, Q4_K weights are
   repacked into an anonymous buffer *and* the mapped file pages stay resident: Qwen3.5-2B peak RSS 1828 MiB
   (mmap) vs 1343 MiB (`--no-mmap` / mlock) on miryam, 2565 vs 1764 on the box; LFM2.5 1216 vs 746.
   Speed and load time are the same within noise. The extra pages are reclaimable page cache, but they
   count toward a cgroup `MemoryMax` and toward any RSS-based watchdog (that is what killed the box runs,
   below). Not changed in this pass; see "Next".
6. **The HD 620 (Vulkan) stays worse than the CPU**: Qwen3.5-2B tg 2.02 vs 6.68, pp512 25.5 vs 26.8;
   LFM2.5 tg 3.29 vs 14.2. Same conclusion as the 2026-10-10 profile.
7. **Laya is an encoder** (`GGML_ASSERT n_ubatch >= n_tokens`): it needs `-ub >= prompt length`, so the
   ubatch sweep doubles as a prompt-length sweep for it. Throughput falls slowly with length (box pp128 1395,
   pp1024 1060; miryam pp128 66, pp512 60).
8. **Speculative decoding with a Qwen3.5-0.8B draft does not pay on CPU** (box, llama-server, Qwen3.5-2B
   target, 512-token code answer): no draft 28.8-30.6 tg; `draft-simple` n-max 8 19.2 (60 % accepted),
   n-max 3 22.6 (80 % accepted); a back-to-back re-run gave 30.6 without the draft and 23.8 with n-max 3 (82 % accepted). The draft costs about as much per token as it saves, and adds
   ~1.3 GiB RSS. Model-free `ngram-mod` was neutral on this prompt (27.8 / 30.9), consistent with the
   2026-10-10 result that n-gram lookup helps edits that repeat the input, not fresh answers.
9. **No thermal throttling seen** on miryam (throttle counters unchanged, max 83 C on CPU runs), but the
   CPU never reported above its 2500 MHz base clock, so turbo looks unavailable in the current power mode;
   a turbo-enabled run could be faster (unverified).
10. miryam is 20-25 % slower than on 2026-10-10 for the coder (tg 6.5 vs 8.4 at -t 2): the desktop session
    (browser, Grok Bot app; load average ~2 before the run) was busy throughout. These are "with the desktop
    in use" numbers.
