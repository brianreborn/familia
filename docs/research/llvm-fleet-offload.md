# Offloading LLVM work across the Familia fleet

**Issue:** [#697](https://github.com/brianreborn/familia/issues/697)<br>
**Research snapshot:** 2026-11-22 (America/Los_Angeles)
**Status:** design research; no execution service or fleet changes are authorized by this issue.

## Recommendation

Familia should own **placement policy, authorization, resource admission, leases, lifecycle, and provenance**. It should not grow a second compiler frontend or invent a new universal compilation protocol. Represent work as immutable, content-addressed actions with declared inputs, outputs, toolchain identity, platform requirements, and an execution profile. Keep build-system dependency discovery in the build system or a proven client adapter, and make execution backends replaceable.

Treat this as a family of workloads, not one “remote compile” operation:

1. **Ordinary compile actions:** best handled through a compiler-cache/distribution wrapper or a build system using remote execution.
2. **ThinLTO backends:** unusually good first LLVM-specific integration target because Clang/LLD expose a distributor hook at the link step.
3. **PGO and post-link optimization:** explicit multi-stage work orders, with profiles tied to the exact instrumented build, workload, toolchain, target, and optimization stage.
4. **IR transforms, module builds, JIT, and accelerator/offload work:** typed action families with their own dependency and latency semantics. Do not claim them as supported merely because an arbitrary command can be launched remotely.

The design should be compatible with the [Bazel Remote Execution API (REAPI)](https://github.com/bazelbuild/remote-apis), especially its `Command`, `Action`, Content Addressable Storage (CAS), Action Cache, execution operations, and log-streaming concepts. The API already models declared inputs/results and content-addressed transfer; its documentation explicitly notes that servers may choose any worker satisfying action requirements, and that repeatable actions are the precondition for safe result reuse. Familia may initially delegate execution to an existing REAPI service. A later Familia-owned executor can reuse the action/CAS model without requiring Familia to implement an entire build system.

Do not put the full REAPI server, a custom compiler wrapper, and a new scheduler into the first implementation. First prove one narrow job path and its lifecycle against existing Familia queues and leases. Keep local execution available, and use measured transfer plus queue delay to decide when remote execution is worthwhile.

## Prior-art comparison

Cache-key correctness depends on correctly capturing inputs. | A useful transparent local/shared cache alongside any scheduler, but it cannot consume a Familia worker lease to execute a miss. | Complement, not offload architecture. Its documented single-file scope and fallback behavior are a reminder not to confuse caching with remote execution. [Manual](https://ccache.dev/manual/latest.html) |

Pump's headers are a useful precedent for explicit dependency closure. | Lightweight baseline for homogeneous trusted hosts; weak fit for a heterogeneous, integrity-aware fleet. [Distribution](https://fastbuild.org/docs/features/distribution.html), [Compiler configuration](https://fastbuild.org/docs/functions/compiler.html) |
| **REAPI and implementations** (Buildbarn, BuildFarm, BuildGrid, BuildBuddy, NativeLink, others) | Declared command actions, remote execution, CAS transfer, action cache, operation status, and often logs. It is broader than C/C++ and can cover link, test, codegen, and utility actions. | Build-system clients construct a declared input root; CAS uploads only missing content by digest. Toolchains and sysroots must be inputs or provisioned by a declared execution platform. | Digests detect changed bytes; sandboxing, authenticated transport, tenancy and cache policy are implementation/configuration responsibilities. A digest does not establish semantic correctness or benign output. | Best standards-based substrate for action/data representation. Existing REAPI servers normally own their worker scheduler; Familia can first delegate, then decide whether to implement a compatible worker/control adapter. | Strongest general foundation; operationally expensive to implement as a full service. Reuse an implementation instead of writing CAS, action cache, and execution API from scratch. [REAPI](https://github.com/bazelbuild/remote-apis), [server landscape](https://github.com/bazelbuild/remote-apis#servers) |
| **Reclient / Goma-style clients, Recc, Siso** | Wraps compiler/build actions and sends them to a REAPI service; Reclient can perform dependency scanning, cache lookups, remote execution and output retrieval. Siso and build-system integrations vary in how they model actions. | Client discovers/declares source dependencies, uploads inputs/toolchain to CAS, then fetches declared outputs. Build-system integration and dependency scanners are material parts of correctness. | REAPI security depends on backend; client-side compare/racing modes and logs help find divergence but are not general verification. Credentials and environment allowlists need careful scoping. | Reclient is a useful adapter model: the compiler/build system stays in charge of action discovery and Familia chooses or supplies the REAPI endpoint/backend. Avoid embedding a second dependency scanner in Familia. | Prefer existing REAPI clients for supported build systems rather than writing wrappers for each one. Verify platform support and licensing before selecting a client. [Reclient](https://github.com/bazelbuild/reclient), [REAPI clients](https://github.com/bazelbuild/remote-apis#clients) |

These introduce ordered dependency edges beyond independent source-file compiles. | `clang-scan-deps` can emit P1689 dependency information for named C++ modules. Module artifacts must be keyed to the compiler, flags, module map, target and imported module closure. | A cache digest must include all module inputs and configuration. A stale or mismatched module artifact can make the result incorrect even if transfer checksums match. | Model as DAG actions with outputs that later actions consume; use leases per ready action. Do not send a module compile before its dependencies are built and committed. | Extend after ordinary compile actions. The dependency graph and artifact identity are the hard part, not remote process launch. [Clang modules](https://clang.llvm.org/docs/StandardCPlusPlusModules.html), [dependency scanning](https://clang.llvm.org/docs/StandardCPlusPlusModules.html#discovering-dependencies) |

DTLTO lets LLD call an external distributor during the normal link and handles cases such as bitcode in archives. | Each backend needs bitcode, the relevant index/import data, target/CPU/options, and the compatible Clang/LLVM toolchain. DTLTO avoids requiring the build system to manage dynamic ThinLTO backend dependencies. | Action and output digests can verify transfer; compiler identity and the linker-generated job metadata must be recorded. A validated link/build is still needed to trust the output. | Excellent bounded integration point: a distributor client can submit backend actions to the existing job queue and return outputs to LLD while Familia leases suitable workers. [ThinLTO](https://clang.llvm.org/docs/ThinLTO.html), [DTLTO](https://www.llvm.org/docs/DTLTO.html) |

SamplePGO/AutoFDO uses externally sampled profiles rather than instrumentation profiles; these formats are not interchangeable. | Profiles must be paired with the matching instrumented binary/build, compiler/profile format, target and workload. Profile merge is a separate, parallelizable data-processing action only once all inputs are identified. | Profile provenance and integrity matter: profiles can be stale, incomplete, contaminated or from the wrong binary. Record build IDs, profile kind, workload identity and merge parameters; require an authorized validation step before promotion. | Represent phases as a bounded work-order DAG; reserve dedicated CPU for instrumented workloads and build phases only when requested. Workloads may need access to test data or services and should not be silently fanned out. | High fleet value, but phase graph and profile validation must be first-class. Do not model PGO as “compile remotely.” [Clang PGO](https://clang.llvm.org/docs/UsersManual.html#profile-guided-optimization), [LLVM PGO build workflow](https://llvm.org/docs/HowToBuildWithPGO.html), [SamplePGO](https://llvm.org/docs/SourceLevelDebugging.html#sample-profiling) |
| **BOLT / post-link optimization** | Profiles and optimizes an already linked native binary, primarily layout and binary-level transformations. | Needs exact binary, matching profile, debug/build metadata where applicable, target architecture, BOLT toolchain and explicit output. | Keep binary/profile provenance; compare functional tests and measured performance before accepting. The transformation is not covered by source-level cache keys alone. | A separate action after link/profile collection, potentially memory- and CPU-intensive; schedule by host/target compatibility. | Include as a distinct action family after PGO lifecycle is defined. [LLVM Advanced Builds](https://llvm.org/docs/AdvancedBuilds.html#bolt) |
| **IR / bitcode pipelines (`clang -emit-llvm`, `opt`, `llc`, `llvm-lto2`)** | Each pass/tool invocation can be a declared action; pipelines can also stream intermediate IR through pipes. | File-based IR is straightforward CAS input/output. Streaming stdin/stdout needs a multi-stage process contract and may be slower when network transfer dominates. Pin exact pass pipeline, plugin set, target, and tool versions. | Same digest/provenance model as remote actions; verify outputs by downstream link or validation. | File-boundary actions map well to queue leases; live pipes and tiny pass steps usually do not. Keep pipeline grouping local when that avoids needless round trips. | Support through generic action execution only after the action contract exists; do not add bespoke RPC for each LLVM tool. |
| **Compiler daemons / libraries** (clangd, clang service processes, compiler-as-library integrations) | Keep compiler/frontend state warm, answer repeated parse/index/compile requests, or embed Clang in another process. These are long-lived services or libraries, not independent compile actions by default. | Need a stable source snapshot, compile database, headers/modules and a session/cache invalidation model. Shipping one invocation's closure does not automatically reproduce a warm daemon's state. | Session identity and invalidation affect correctness; daemon state must not silently cross project, principal or integrity boundaries. | Poor first fit for ordinary queue leases. Keep daemons local to a host or expose a purpose-built long-lived service/session with its own resource lease. | Track separately from batch compilation; do not call clangd itself a distributed build system. |
| **ORC/JIT and remote JIT** | Compiles and links units on demand as a live process resolves symbols and continues execution. Some LLVM APIs can target separate processes, but a remote JIT is a session/runtime problem, not just batch compilation. | May move IR/object code, symbol-resolution requests, runtime libraries and execution state repeatedly; session affinity and low latency matter. | Requires runtime/session identity, code provenance, isolation and a clear trust boundary; a verified object hash does not constrain execution behavior. | Poor fit for ordinary queue leases because work is latency-sensitive and stateful. A persistent, explicitly authorized execution session would be needed. | Keep out of the initial batch offload scope. Treat JIT as a later service/session feature. [ORC design](https://llvm.org/docs/ORCv2.html) |
| **GPU/offload toolchains (CUDA, HIP, OpenMP offload, etc.)** | Device code compilation and, in some workflows, device execution or profile collection. | Requires exact compiler/runtime/SDK plus target architecture and sometimes device runtime libraries. Device output is architecture-specific. | Device driver/runtime and worker identity must be recorded; compilation success does not prove the device path can execute. | Familia's coupled CPU/GPU memory admission and accelerator capability/quarantine decisions are relevant, but compile jobs and runtime kernels need distinct resource classes. | Keep as a capability-gated extension; do not infer accelerator availability from a compiler being installed. |
| **Academic/older systems** (DiSCo, HTCondor+distcc, research compile farms) | Explore moving preprocessing, compilation and linking at varying granularities; several build on existing tools and batch schedulers. | Common themes are dependency analysis, minimizing transfer, shared filesystem/cache, or explicit compile-command extraction. | Usually application-specific; not a production integrity contract for a federated fleet. | Useful evidence that submission queues can distribute compile work, but they do not remove the need to define action inputs, trust and result acceptance. | Do not adopt a research prototype over REAPI or a maintained compiler service without a measured need. [DiSCo paper](https://www.jstage.jst.go.jp/article/transinf/E96.D/3/E96.D_589/_pdf/-char/en), [HTCondor + distcc proceedings](https://ceur-ws.org/Vol-2507/135-141-paper-23.pdf), [sdcc project report](https://www.scs.stanford.edu/14au-cs244b/labs/projects/sdcc.pdf) |

This survey covers the systems and categories named by the issue plus the adjacent LLVM mechanisms. It is not a claim that every commercial product, private service, or research prototype has been exhaustively benchmarked. The central distinctions found across the sources are: **cache vs execute; compile invocation vs declared build action; data transfer vs dependency closure; and stateless batch work vs stateful runtime work.**

## Review of the prior Grok Bot research on #697

Grok Bot's earlier comment found the right high-level seam: REAPI-shaped actions, content-addressed inputs, and DTLTO as a narrow first integration. Several parts should remain hypotheses rather than requirements until checked against Familia's existing design and current upstream behavior:

- **Do not add a second “forge” scheduler or nested coordinator model.** Familia already has queue/lease decisions in #685. A job may contain dependent actions, but actions should use the existing work-order and lease machinery unless a measured need demonstrates a distinct scheduler. The external REAPI provider can own execution when Familia delegates to it; Familia must make that ownership boundary explicit.
- **DTLTO is a promising adapter, with important version limits.** Upstream defines a JSON file of common args/inputs plus per-job args, inputs and outputs, and requires matching Clang/LLD and a distributor compatible with that LLD JSON schema. Current docs say DTLTO is limited to ELF and COFF, supports only a limited set of codegen configurations, and cannot share ThinLTO cache entries with in-process ThinLTO because identical code generation is not yet guaranteed. The first prototype must preserve linker-visible paths/outputs and test failure/cancellation behavior; it cannot assume every index/import artifact is already in the JSON inputs. [LLVM DTLTO docs](https://www.llvm.org/docs/DTLTO.html), [LLD DTLTO constraints](https://lld.llvm.org/DTLTO.html).
- **Do not use `clang-scan-deps` as a universal closure oracle.** Clang's C++ modules documentation currently says its P1689 mode supports named modules; ordinary headers, generated files, PCH, system headers, macros and build-system-specific inputs still need correct dependency discovery. Prefer the build system's declared inputs or an adapter already used by that build, then add module scanning where needed. [Clang modules dependency discovery](https://clang.llvm.org/docs/StandardCPlusPlusModules.html#discovering-dependencies).
- **Cross-compiling targets does not make host executables portable.** Clang can target another CPU/ABI when it runs, but a worker still needs a compiler executable and host libraries that run on that worker's OS/architecture, plus the right target sysroot. A Termux phone is not interchangeable with a Linux x86 worker simply because both can emit an object for the same target triple.
- **REAPI does not imply a Familia-compatible worker scheduler.** It standardizes action/data APIs and execution operations; server implementations choose their internal scheduler and workers. Running a REAPI server beside Familia may duplicate placement policy. Start by delegating to one provider or by defining a Familia worker adapter; avoid managing one action in two schedulers.
- **Independent duplicate execution is a validation option, not a blanket acceptance rule.** Matching output digests on two workers provide useful evidence but do not prove correctness when they share a toolchain, compromised input/cache, or build defect. An owner-host result is not automatically trusted either. Keep the user's prior requirement that promotion needs a distinct authorized validator; specify the validator's evidence and authority per integrity policy.
- **Do not hard-code host-specific guesses into the design.** “Phones only take small jobs,” “PGO sampling is unavailable on phones,” and universal release-build double execution are possible policies, not general facts. Determine eligibility from declared action requirements and live host capabilities; let enterprise policy decide validation cost.

The LLVM CAS/dependency-scanning work is useful direction, but the cited LLVM CAS material is an RFC and experimental work, not a stable general-purpose Familia dependency protocol. Likewise, claims that a particular build client has been retired from a project, or that a project has “settled” on one ecosystem, need dated primary-source evidence before they become design assumptions.

## Familia design sketch

### 1. Work description

Define a versioned action envelope before implementation. It should describe:

- action family and entry point (compile, ThinLTO backend, profile merge, PGO workload, post-link, IR transform, module build, JIT session, device compile);
- immutable input manifest and root digest, declared output paths/types, and optional cache policy;
- exact toolchain identity: executable/build digest, plugins, sysroot, target triple/CPU/ABI, relevant runtime/SDK, flags and controlled environment;
- host requirements: OS/architecture, available memory, CPU class, accelerator/driver where relevant, and required isolation features;
- work-order/federation scope, purpose, deadline, cancellation/drain policy, integrity label, and data retention;
- parent action/dependency IDs and a bounded resource request (CPU, memory, accelerator, transfer bytes, expected duration).

The source build system or a known client adapter should produce the dependency closure. Never infer that copying one source file is enough for a compile. Inputs and outputs move only over user-authorized edges; the current SSH nexus precedent already names artifacts by SHA-256 and verifies transfers, but it is storage transport, not an execution protocol ([transport PoC](../transport-poc.md)).

### 2. Execution and scheduling

Keep an action's content identity separate from its scheduling attempt. A lease binds an attempt to a worker and expires; a fencing/attempt token prevents a late worker from overwriting the accepted result after retry or cancellation. A job can be locally executed, sent to an external REAPI provider, or run by a Familia worker adapter. Record queue time, transfer time/bytes, worker selection reason, execution duration, fallback/racing behavior and final state.

Use the owner-approved #685 decisions as constraints: per-host run queues and ULE-style load/interactivity policy; coupled CPU/GPU memory admission for shared-memory hosts; pairing CPU+GPU claims for split offload; quarantine after device loss; and local-fleet-first routing with federation spill only when local capacity cannot take the job. A workload may declare a CPU dedication requirement, but the scheduler must account for memory, target compatibility, bandwidth and the user's focus/capability ceiling too. The job itself does not grant CI/CD credentials: credentials belong only to work orders that need them.

Keep action-level caching optional and scoped by action digest, toolchain/platform identity, and the configured trust boundary. A hit is a cache result, not a scheduled task. A cache miss may run locally or remotely according to explicit policy and measured transfer/queue cost. Never hide a remote fallback or race: report which execution won and retain the other attempt's status.

### 3. Trust, integrity and acceptance

Hashing proves that received bytes match a digest; it does not prove the compiler was honest or the output is correct. Record the worker principal, host, executor version, action digest, attempt/lease, toolchain digest, logs, exit status and output digests. Run actions in an isolated, disposable environment with a minimal declared environment and no ambient credentials by default. Do not permit an action to publish into a trusted cache or alter a protected worktree merely because it completed successfully.

Keep each result's integrity label and provenance. A combined build result inherits the lowest-integrity contributing result unless a distinct authorized validator promotes it. Validation can range from local re-execution or cross-worker comparison to project tests, reproducible-output checks, profile-specific workload checks, and a maintainer-approved promotion policy. Different validation strength should be explicit; duplicate execution is evidence, not proof, if workers share the same compromised toolchain or source of inputs.

### 4. Workload-specific workflows

- **Compile / modules:** consume a build-system action, exact dependency root, compiler bundle and outputs; make module import edges explicit.
- **ThinLTO:** use the LLD DTLTO distributor interface as the first integration experiment. Keep the thin-link/link process as coordinator and distribute only backend actions with their index/bitcode/toolchain closure.
- **PGO:** create a bounded DAG for instrumented build, workload collection, profile merge and optimized rebuild. Bind profiles to the instrumented build ID and workload declaration. Treat sampled profile capture as a distinct method from instrumentation.
- **BOLT:** run as a separate post-link transformation with the exact binary/profile/target tuple, then validate behavior and measure the intended metric.
- **IR passes:** batch only when file outputs are meaningful; keep low-cost stream pipelines local when network round trips dominate.
- **JIT and device execution:** require explicit long-lived session or device execution resources; they are later scopes, not a generic worker switch.

## Staged follow-up issues

1. **Action and artifact contract ADR:** choose the versioned envelope, canonical action identity, leases/retries/fencing, integrity provenance, cancellation and cache-scope semantics. Map it to Familia graph nodes, authorized transport edges, work orders, and existing queues.
2. **ThinLTO distributor prototype:** build a small DTLTO adapter that submits backend jobs to a queue, stages content-addressed inputs/outputs, handles cancellation and local fallback, and compares total link time against local LLD backends. This is a bounded proof that queue leases can support real compiler work.
3. **REAPI integration spike:** select one supported build client and a maintained REAPI executor/cache provider; determine whether Familia delegates dispatch or supplies workers. Compare setup cost against sccache-dist and record host/platform coverage before committing to a backend.
4. **PGO/AutoFDO/BOLT lifecycle:** define profile provenance, workload declarations, data retention, CPU/memory reservations, profile merging and authorized result promotion.
5. **Execution isolation and validation:** document sandbox requirements, worker identity, allowed environment/credentials, cache poisoning response, reproducibility checks and validator authority.
6. **Capability-specific extensions:** module/PCH dependency materialization, additional build-system adapters, accelerator compilation/execution and remote JIT sessions. Open each only when a concrete workload and latency/transfer measurements justify it.

## Source notes

Primary project documentation was preferred. The online project/API documents are moving references; this report reflects the linked docs as accessed for this research snapshot. The issue's initial list also names Buck2, BuildBuddy, Buildbarn, NativeLink, Goma/Reclient/Siso, and academic work: the REAPI survey includes the servers and build-system clients as an ecosystem rather than treating every vendor as a separate protocol.
